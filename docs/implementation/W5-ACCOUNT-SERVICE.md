## API and integration contracts

All private reads and writes require `X-Wishlyn-Account-ID` matching the verified session. This header is only a captured-client-account precondition; it never selects an owner or grants access. A missing or different header returns 409 `account_changed` before application reads/writes. All owned browser mutations additionally use same-origin protection, streamed JSON limits, server sessions and distributed request budgets. Private reads use `Cache-Control: no-store`. Identity is selected exclusively by the verified session. Successful private responses include `viewerId`; customer-owned payloads are separately checked against the intended account. Staff support uses staff `viewerId` and keeps the customer `request.ownerId` distinct. `accountRequest<T>(url, intendedAccountId, body?, signal?)` checks the captured account before sending and after receiving, rejects a verified A/B/A cycle, and validates response identity. Recovery/reset are the only public calls and pass a null account. Reload controls verify the session before retrying. Password and recovery paths have additional abuse budgets before expensive work.

- `GET/POST /api/account/profile`: `{ profile: { ownerId, email, firstName, lastName, version } }`. POST edits names/version; email/role remain server authority.
- `GET/POST /api/account/addresses`: `{ ownerId, addresses: [{ id, version, label, firstName, lastName, phone, address, city, state, zipCode, country }] }`. POST creates without ID, updates with owned ID/version, or deletes with `{ action: 'delete', id, version }`. Root's W6 integrates selection into checkout; saving an address does not establish delivery eligibility.
- `POST /api/account/password`: `{ currentPassword, newPassword }`; success clears the session cookie after all-session revocation commits.
- `GET/POST /api/account/wishlist`: `{ ownerId, items, version, browserImported }`. Mutations use `add/remove/toggle` plus `productId`, a once-only legacy `import` plus `productIds`, or explicit guest `transfer` plus up to 50 `{ id, productIds }` records in `transfers` (the single UUID `transferId`/`productIds` form remains supported); entire-list replacement is not accepted. Guest selection IDs are created and persisted under the browser store Web Lock, stay stable per product when other guest picks change, and have persistent owner claims. Delayed tabs reuse those IDs instead of minting a second transfer. Guest migration waits for that lock. Cart migration chooses one authoritative guest copy and preserves exact quantities and gift lines, including its storage fallback. Account-scoped pending transfer records persist separately from legacy lists and are acknowledged only after a verified server response. Each selection ID is consumed independently in a bounded batch transaction; spent selections are skipped when a batch also includes new selections. Server transfer IDs commit with the owned wishlist and make replay safe after an uncertain response or failed browser acknowledgement; replay returns current state and cannot resurrect a later removal. Keep spent IDs while clients may replay them. Queued UI toggles become deterministic add/remove intent and pause through verification; a verified account change discards them.
- `POST /api/account/recovery`: `{ email }`. Disabled configuration returns 503. Configured requests return the same 202 acceptance text for unknown accounts and failed/uncertain delivery; that text asks the user to check email and makes no sent-email claim.
- `POST /api/account/reset-password`: `{ token, newPassword }`. Consumption/profile change/session revocation share one transaction. Outstanding links can finish safely if issuance is disabled later.
- Customer `GET/POST /api/support`, `GET/POST /api/support/[id]`; staff `GET /api/admin/support`, `GET/POST /api/admin/support/[id]`. Creation requires a valid owned order, request UUID, kind, subject and bounded message. Replies require current version; staff choose status and a customer reply reopens a resolved request. Pages are bounded to 20 requests and conversations to 200 events.

`src/lib/account/types.ts` exports the shared account/address/wishlist/support types. Existing purchase snapshots, payment state, reservation counts and fulfilment are not changed by service requests. Receipts remain distinct from statutory invoices.

### Shared cart recovery contract for W6

`cartStore.getEligibleGuestRecovery(expectedAccountId)` returns only fresh, unpersisted guest additions for the currently verified intended owner. The cached shared guest snapshot is never eligible after a failed storage read. For matching cart lines, only the locally added quantity is returned; unchanged shared quantity and distinct shared gift lines remain withheld. `cartStore.consumeGuestRecovery(expectedAccountId)` clears those local deltas after assignment and also checks current identity. Both methods use the internal `eligibleGuestMemory`/`consumeLocalGuest` helpers. Consuming local deltas after an unread guest fallback preserves any unresolved UUID-bound shared negative journal for that owner until shared verification completes. W6 must preserve the full shared store and add purchased-bag cleanup separately.

Both normal and cached-account paths call `claimLiveCartGuest(owner, livePersistedGuestItems)` under the shopping Web Lock. It returns `{ items, complete }`: `items` contains only newly durably claimed shared selections; every previously claimed ID is spent and skipped. `complete: false` keeps the unverified remainder retained for retry and never publishes that remainder as owned. Merge the claimed shared portion and eligible local additions once, consume local additions, and delete consumed guest memory. A cart-only owner-keyed memory Map preserves visit-only bags through same-owner loading/error and A/B/A verification while hiding private data until identity is verified. Logout starts with an empty guest bag; genuinely new guest actions can merge into a prior account's visit-only bag exactly once. Returning focus verifies the session and retries retained selections; explicit store retry forces revalidation for unresolved guest assignments or owner memory.

Memory entries distinguish `baselineKnown` from an unread owner cart. An unread empty fallback never authorizes replacing durable account data. Accepted owner-local update functions are retained in memory while the baseline is unread, including safe guest additions already bound to that owner. `restoreCartMemory` runs under the same lock on retry/reverification and before the next mutation: it reads the durable owner cart, replays those accepted updates exactly once, marks the resulting baseline known, and saves it. If writing still fails after a successful read, the complete known snapshot is retained and the updates are not replayed again. This preserves exact added quantities, explicit quantity/removal intent and account isolation without combining a shared guest snapshot with B. Recovery is visit-only until storage succeeds; update functions and unknown-baseline state are not persisted across page reloads.

The fourth head's re-review found that an unread persisted B cart could be replaced by an empty fallback and a later fresh addition. The fifth revision corrects this with the baseline distinction and restore-before-mutation behavior. Its regressions cover an existing quantity-three gift, recovery with no local edit, a direct later mutation without explicit retry, owner-local additions/removals through B/A/B, same-line guest/owner additions, removal after recovery, working writes with denied reads, and a second quota failure after the baseline returns.

Only fresh unassigned local actions or a newly verified unclaimed guest baseline can populate the guest fallback. Fresh local intent already bound to a queued account migration remains archived for that owner and stays hidden from the new guest session. Guest retries, refreshes, storage events and mutations revalidate claims under the shopping lock, including claim-read failures with readable raw data; guest memory cannot bypass that check. Pending guest edits replay once on the verified unclaimed baseline, preserving explicit cancellations and exact new quantities.

Guest version-2 payloads now also carry `guestSelectionIds`, written atomically with their items. Separate selection records are written before payload replacement and pruned afterward. A failed payload write keeps the old raw copy's original identity; failed metadata cleanup leaves the new payload associated with its own fresh identity. Legacy unannotated raw copies keep their oldest matching record while pending replacement metadata may contain a newer action. Explicit re-selection gets a fresh UUID; fresh cart records match line identity rather than object references. Removed UUIDs are tombstoned as `cancelled` before migration, including the cached-account cart path, without overwriting an existing owner claim. Tests cover identical consumed/fresh product and gift payloads, failed payload/metadata writes, legacy records, direct account verification after cancellation and new/cached owner migration. The public W6 guest recovery and unread-owner journal contracts above remain unchanged.

## Safe recovery delivery setup

Recovery requires all of:

```text
ACCOUNT_RECOVERY_ENABLED=true
APP_ORIGIN=https://the-approved-store-origin
RECOVERY_EMAIL_FROM=<verified sender accepted by Resend>
RECOVERY_EMAIL_API_KEY=<environment-isolated provider credential>
```

The endpoint is fixed to `https://api.resend.com/emails`, verifies an actual provider message ID, and uses a bounded request and provider idempotency key. The adapter passes a plain-text message only. No token, provider response or credential is logged. A token is usable only after delivery is recorded as sent; a timeout/failed response consumes it, even if a provider later delivers that message. The customer must request a fresh link. This favors safe recovery over treating ambiguous provider success as a usable credential.

Operator acceptance still requires approved sender/domain verification, isolated preview/production credentials, real provider sandbox/allowlisted mailbox testing, delivery monitoring and an operated escalation channel. No live mailbox/provider was used here. Unknown accounts and delivery failures receive identical acceptance semantics to avoid disclosing account existence through provider outages. Monitor aggregate `delivery_state`/expiry counts rather than raw tokens, email payloads or password values. Purge expired/consumed tokens after the approved security retention period; retain aggregate delivery failures for operations. Do not re-enable or resend a failed token.

The workflow has no automated transactional purchase/support notifications. Customers and staff follow replies in the store; notification delivery, retries and exception monitoring remain E5 setup work rather than simulated email. Guests must create/sign into an account to recover owned data/orders. Guest checkout remains deliberately deferred in the main implementation plan.
