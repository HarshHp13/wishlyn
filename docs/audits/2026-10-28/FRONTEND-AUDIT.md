## Assessment

The storefront's normal browsing path is functional, but failure handling, account-local state, checkout recovery, and accessibility are not ready for a reliable commerce launch. The high-priority frontend finding is a checkout dead end after a failed payment SDK load. Shared-browser account-data exposure is P2, matching the security audit's scope and severity: another person using the same browser profile is the prerequisite. The remaining findings are medium- and lower-priority interaction, accessibility, operability, and capability gaps.

The previously reported product-page error did **not** recur in a fresh browser. The parent verified all 25 products in the preceding task, and this audit independently opened representative product pages, including a long title and a missing product. The recently changed header logo is centered and uses the symbol-only asset. Neither historical problem is counted as a current defect.

No application code was changed. All browser data used below was confined to an isolated `audit-frontend` session. Account records and addresses were synthetic. Failed API/SDK responses were injected in the browser. No real payment, order, newsletter subscription, account registration, admin mutation, or upload was submitted.

## Detailed findings

### FE-001 — P1 — Failed payment SDK load leaves checkout permanently processing

**Confidence:** high, reproduced. **Sources:** `src/app/checkout/page.tsx:28-44`, `:141-145`, `:303`, `:453-456`.

The checkout renders the Razorpay `Script` before payment. If it errors while the shipping step is displayed, `loadRazorpayScript()` later finds the existing script and attaches fresh load/error listeners. The earlier error has already fired, so neither listener resolves the promise. There is no timeout, recorded failed status, or script replacement. The failure is conditional on the script failing **before** Pay is clicked; normal payments were not found universally broken.

**Reproduction:** abort `https://checkout.razorpay.com/**` in the isolated browser, enter the shipping step, continue to payment, press Pay. After 1.8 seconds the button still reads `Processing...`, Back is disabled, no feedback appears, and `window.Razorpay` is undefined while the script element exists. The source establishes that the wait is unbounded, rather than merely a slow 1.8-second request. No order request reached the server.

**Impact:** a transient network/content-blocker failure traps the customer at the purchase step; the visible retry route is unavailable.

**Fix:** one shared script-loader state machine that records pending/success/failure, retries failed elements and rejects after a bounded timeout. Render a recoverable error and keep Back usable when initialization fails.

**Acceptance:** fail the initial script fetch, then restore network access. Pay must produce a timely, announced error and offer a retry that loads a fresh script successfully without a page reload.

Evidence: [checkout-audit.json](frontend/checkout-audit.json), [checkout-sdk-failure.png](frontend/checkout-sdk-failure.png).

### FE-002 — P2 — Cart and addresses cross account boundaries in a shared browser

**Confidence:** high, reproduced with synthetic accounts. **Sources:** `src/context/CartContext.tsx:93-99`, `:119-125`; `src/app/checkout/page.tsx:86-98`, `:118-128`; `src/lib/authClient.ts:67-79`.

Every account cart is copied to the global `wishlyn-cart` key. Any empty account or empty guest cart imports that global cart. Shipping addresses use one global `wishlyn-saved-addresses` key and are neither partitioned by account nor cleared at sign-out. The checkout preserves the new account email while filling the previous account's name, phone and street address, creating a particularly plausible wrong-recipient combination.

**Reproduction:** synthetic A cart contained a gift message for Alice; after account switch, synthetic B's cart contained the same line/message. Separately, with B active, an A address fixture was automatically filled into checkout while email remained B. The saved cart and address fixtures contain no real customer data.

**Impact:** disclosure of purchase intentions, gift text and contact/address data to the next person using the device; accidental delivery to the wrong person.

**Severity/scope:** P2 aligns with SEC-009 because the demonstrated condition requires account switching within the same browser profile. No remote cross-user disclosure or arbitrary server-side customer-data access was established. Both the legacy-cart fallback and global saved-address key remain part of this canonical privacy finding.

**Fix:** isolate stored data by verified account identity; explicitly define one-time guest-cart migration; do not use a previous account's cart as a universal fallback. Separate saved addresses by account and handle logout/cache transitions consistently.

**Acceptance:** A → sign out → B → sign out must never expose A's cart, message or address. Empty carts must stay empty. Guest migration should occur once under an explicit tested policy.

Evidence: [interaction-audit.json](frontend/interaction-audit.json), [checkout-audit.json](frontend/checkout-audit.json). **Deduplication:** SEC-009 owns the consolidated privacy issue; this entry supplies frontend reproduction and impact, not a second independent security incident.

### FE-003 — P2 — Different gift messages are silently merged

**Confidence:** high, reproduced. **Sources:** `src/context/CartContext.tsx:142-153`, `:165-166`; `src/components/CartDrawer.tsx:139-143`.

Cart identity is only variant plus gift-wrap boolean. Add a gift with message “Audit gift for Alice”, close the drawer, change the text to “Audit gift for Bob”, and add the same variant again. The cart becomes quantity two with only Alice's message. The drawer shows Gift Wrapped but does not expose the stored message for review/editing.

**Impact:** the order payload loses an intended personalization without warning, potentially giving two recipients the wrong message.

**Fix:** include personalization in line identity or provide an explicit edit/replace flow; display gift text in the bag and order summary.

**Acceptance:** two same-variant gifts with distinct messages retain both instructions through bag, checkout, persistence and order payload; identical gifts may merge only under an explicit rule.

Evidence: `giftMerge` in [interaction-audit.json](frontend/interaction-audit.json).

### FE-004 — P2 — Invalid shipping fields advance to payment

**Confidence:** high, reproduced. **Sources:** `src/app/checkout/page.tsx:115-132`, `:380-403`, `:406-412`.

Phone and postal fields are required but have no format validation. An Indian address with phone `111` and postal code `xyz` advances to Payment Details. Street/city/state values are only checked for nonempty input; whitespace is not normalized. Five destination countries are offered despite a single flat shipping calculation and India-specific fulfillment copy; actual international support needs a business/backend decision.

**Impact:** customers can reach payment with unusable contact or delivery details. The frontend does not help them correct likely mistakes before a financial action.

**Fix:** validate normalized phone/postal/address fields for supported countries, show linked inline errors, add appropriate autocomplete/inputMode hints, and constrain country choices to supported fulfillment coverage. Backend validation is still mandatory.

**Acceptance:** invalid Indian postal codes/phone numbers cannot advance; valid supported international addresses use their own rules. Errors are announced and focus the first invalid field.

Evidence: `invalidAddressAccepted` and `inputs` in [checkout-audit.json](frontend/checkout-audit.json). No payment was submitted.

### FE-005 — P2 — Postal lookup failure is shown as successful delivery eligibility

**Confidence:** high, reproduced. **Sources:** `src/components/ProductDetail.tsx:106-158`, `:136-146`; `src/app/checkout/page.tsx:423-458`.

On a network exception, the pincode checker sets `valid: true` and invents an express/standard estimate from the first two digits. A failed lookup for `111111` displayed “Express Delivery: Estimated 2-3 business days. COD available.” Even a successful India Post lookup confirms a postal area, not a shipping service's delivery SLA or COD coverage. Checkout exposes only online Razorpay payment, with no COD choice.

**Impact:** customers receive an affirmative delivery/payment promise when it has not been verified, including during an outage.

**Fix:** report verification unavailable on lookup failure. Use actual courier coverage/SLA data for delivery claims; show COD only where it is supported end to end, or remove the promise.

**Acceptance:** failed postal lookup never reports confirmed eligibility; unsupported/nonexistent codes cannot receive a success promise; any displayed COD offer has a selectable checkout path.

Evidence: `failedPincode` in [interaction-audit.json](frontend/interaction-audit.json).

### FE-006 — P2 — Obsolete async responses can overwrite current state

**Confidence:** high for the code path; out-of-order responses were not timed live. **Sources:** `src/components/ProductDetail.tsx:88-160`, `:352-358`; `src/app/wishlist/WishlistGrid.tsx:15-42`.

Postal lookups have no abort controller or request-generation check. If code A's request finishes after code B's request, A's result is shown beside B; clearing/changing to an incomplete code can also be undone by an old response. The wishlist effect likewise has no cleanup/ignore guard: a slow response for an earlier wishlist/account can overwrite the products after the current IDs have changed or been cleared.

**Impact:** incorrect delivery feedback and stale/removed wishlist cards can be displayed. This entry does not claim that saved IDs are deleted.

**Fix:** cancel obsolete requests or compare a request identity before committing state; derive all displayed state from the current inputs/account generation.

**Acceptance:** deterministic tests complete A after B and clear the wishlist during an in-flight request. Only B/current IDs may appear, with no stale cards or status.

### FE-007 — P2 — Request failures are falsely presented as empty data

**Confidence:** high, reproduced with injected 500/503 responses. **Sources:** `src/app/wishlist/WishlistGrid.tsx:25-38`, `:67-79`; `src/app/admin/page.tsx:123-155`, `:753-761`.

Wishlist failure only logs to console or ignores a non-OK response, then exits loading with an empty product array. The UI simultaneously says “1 item you love” and “Your wishlist is empty.” The admin catalog loader similarly logs the exception and shows “No products in Neon Database ... add your first ...” after a failed fetch. Both omit an error state and retry control.

**Impact:** users are told their data is absent when the service is unavailable. Administrators may try recreating existing inventory. Saved wishlist IDs were still present in the reproduced failure; this is misleading presentation, not proven deletion.

**Fix:** distinguish loading, success-empty, success-populated and error states; retain prior data where appropriate and offer retry with understandable feedback.

**Acceptance:** 500, offline and malformed-response scenarios show an announced error/retry state, never a genuine-empty claim; retry restores existing items without re-entry.

Evidence: [wishlist-outage.png](frontend/wishlist-outage.png), [interaction-audit.json](frontend/interaction-audit.json), [admin-filter-audit.json](frontend/admin-filter-audit.json).

### FE-008 — P2 — Persisted cart prices and availability are never refreshed

**Confidence:** high, confirmed code path; no production catalog change was made. **Sources:** `src/context/CartContext.tsx:45-67`, `:83-104`, `:146-153`, `:179-216`; `src/app/checkout/page.tsx:106-108`, `:157-191`; `src/app/api/create-order/route.ts:32-34`, `:85-97`.

Cart persistence stores full product/variant snapshots and trusts them after reload. There is no reconciliation fetch. Even adding the same item from an updated product page only changes quantity in the existing line; it does not replace its stored product, price or stock. Checkout calculates and submits an explicit amount from that snapshot. The active creator accepts `body.amount` directly and skips its item-repricing branch; it returns the resulting gateway order amount, not a freshly authoritative catalog quote. A stale amount can therefore be passed through to payment unchanged. This is confirmed source behavior, not an observed real charge.

**Impact:** customers see stale prices/stock and can reach payment with removed/unavailable items; an outdated low price can be charged unchanged under the current creator logic. This intersects the backend/security canonical payment amount-trust finding. Independently, refreshing the bag and explaining changed availability is still a frontend requirement after the server amount-trust defect is corrected.

**Fix:** persist identifiers plus user selections, refresh authoritative cart data on load/checkout, reconcile existing lines on add, and require acknowledgement of changed prices/unavailability before payment.

**Acceptance:** change price/stock in a controlled fixture after saving a cart, then reload and re-add the item. The bag and payment confirmation must display current values and explain changes.

### FE-009 — P2 — Shopping contexts remain stale in other tabs

**Confidence:** high; wishlist reproduced, cart has the same subscription omission. **Sources:** `src/context/WishlistContext.tsx:61-81`; `src/context/CartContext.tsx:106-127`; compare `src/components/Header.tsx:30-36`.

The providers listen only for the same-window custom auth event, not the browser `storage` event. Two tabs share updated localStorage, but the second tab's wishlist remains unchanged until reload. Reproduced first-tab header: “Wishlist (1 items)”; second-tab header: “Wishlist”; second-tab storage already held the product ID. Cross-tab auth changes also leave cart/wishlist identity stale, while Header separately observes storage and may display the new identity.

**Impact:** inconsistent shopping state, lost updates from competing tabs, and an account header that can disagree with the underlying shopping data.

**Fix:** use a shared external store or storage/BroadcastChannel synchronization keyed to account identity, with explicit conflict handling.

**Acceptance:** additions, removals and sign-out from one tab update all other tabs without reload and never overwrite newer data.

Evidence: `crossTab` in [state-audit.json](frontend/state-audit.json).

### FE-010 — P2 — A malformed persisted cart crashes the entire storefront

**Confidence:** high, reproduced with synthetic data. **Sources:** `src/context/CartContext.tsx:45-67`; `src/components/CartDrawer.tsx:113-119`; `src/app/layout.tsx:39-44`.

The cart parser accepts any truthy `product` and `variant` objects. The root-mounted drawer renders their nested fields even when closed. Store `[{"quantity":1,"product":{},"variant":{}}]` under the isolated guest-cart key and reload: the page throws “Cannot read properties of undefined (reading '0')” while accessing product images and shows a page-load failure. The bag does not need to be opened. Reload alone retains the malformed record.

**Impact:** stale/corrupted persisted data can lock a browser out of all routes. This was an intentional resilience test, not a recurrence of the earlier clean-session product-page error.

**Fix:** validate/version persisted records deeply, discard or quarantine incompatible lines and tolerate storage failures. Keep a malformed cart from taking down the root application.

**Acceptance:** malformed/missing product images, variant prices and IDs recover to a usable storefront with a clear cart-recovery message; repeated reloads remain usable.

Evidence: `corruptCart` in [state-audit.json](frontend/state-audit.json).

### FE-011 — P2 — Core form fields lack associated accessible labels

**Confidence:** high, source and DOM confirmed. **Sources:** `src/app/login/page.tsx:164-188`; `src/app/admin/page.tsx:533-692`; `src/components/ProductDetail.tsx:306-314`.

The visible login and admin labels have neither `htmlFor`/matching input IDs nor wrapping relationships. The live DOM reports zero associated labels for both login inputs and all 11 admin fields. The gift-message textarea has only a placeholder. Placeholder fallback naming does not provide the persistent, programmatically associated visible labels presented by the UI.

**Impact:** screen-reader/voice-control users cannot reliably identify the same fields sighted users see; clicking labels does not focus their controls. Repeated variant fields have no distinct group identity.

**Fix:** associate labels and descriptions, use fieldsets/legends or equivalent groups for repeated variants, and add stable names/autocomplete tokens for auth/address inputs.

**Acceptance:** accessibility-tree names match the visible labels, label clicks focus the field, repeated variant inputs are distinguishable, and validation errors are associated with the affected fields.

Evidence: [screen-audit.json](frontend/screen-audit.json), `adminFailure.fieldLabels` in [admin-filter-audit.json](frontend/admin-filter-audit.json).

### FE-012 — P2 — Selected controls and async form feedback lack accessible state

**Confidence:** high, source/DOM confirmed. **Sources:** `src/components/ProductDetail.tsx:253-291`, `:369-408`; `src/app/login/page.tsx:118-160`; `src/app/checkout/page.tsx:443-449`; `src/app/admin/page.tsx:522-525`.

Product specification tabs and metal/size controls communicate selection through CSS only. The active Jewellery Care control is a native button and correctly has an **implicit button role**, but has no tab/radio semantics or `aria-selected`/`aria-pressed` state identifying the selected option. Login tabs have the same selected-state problem. Auth/admin/payment status messages are plain containers without live-region semantics or focus/error associations. Keyboard-clickable buttons alone do not expose which option is selected or announce asynchronously inserted errors.

**Impact:** nonvisual users have to rediscover changing content and cannot reliably determine the selected purchasing option or whether an operation failed.

**Fix:** use native radio/select controls or correct tab/button state semantics with documented keyboard behavior. Make success/error feedback live and link field-level errors. Do not give ordinary buttons tab roles without implementing the corresponding keyboard model.

**Acceptance:** keyboard and screen-reader checks identify every active option and announce errors/success once; changing a spec tab exposes a labeled panel and maintains predictable focus.

Evidence: `tabSemantics` in [state-audit.json](frontend/state-audit.json).

### FE-013 — P2 — Gold text and focus indicators have insufficient contrast

**Confidence:** high for the cited color pairs and consumers. **Sources:** `src/app/globals.css:4-13`, `:112-115`, `:135-136`; `src/components/CartDrawer.module.css:250-275`; `src/app/admin/page.tsx:719-738`; `src/components/Editorial.tsx:114-126`; `src/components/Editorial.module.css:94-96`.

Exact sRGB contrast calculations show:

| Pair | Ratio | Affected case |
| --- | ---: | --- |
| `#c6a46a` on white | 2.354:1 | Global keyboard focus outline; admin Add Metal Variant text |
| `#b39054` on white | 2.985:1 | 15px bag item prices and 20px bold bag total |
| `#947039` on ivory `#faf8f3` | 4.268:1 | The 9px “MORE THAN A FINISHING TOUCH” eyebrow in the Brand Story section |

Normal text needs 4.5:1 for WCAG AA; large text needs 3:1; essential non-text indicators need 3:1 against adjacent colors. The shared dark gold passes at 4.53:1 on pure white but does **not** pass for small text on ivory. Logo artwork is not included in this finding.

The concrete ivory consumer is `Editorial.tsx:126` (`<span className="eyebrow">MORE THAN A FINISHING TOUCH</span>`). The global `.eyebrow` rule in `globals.css:135` sets 9px text to `--gold-ink`; its enclosing `.story` section (`Editorial.tsx:114`) gets `--warm-ivory` from `Editorial.module.css:94-96`. The source relationship, exact tokens and WCAG sRGB calculation are saved in [color-contrast.json](frontend/color-contrast.json). The Hero's own eyebrow uses a different text color and is **not** evidence for this row.

**Impact:** prices and keyboard focus can be difficult to see for low-vision users.

**Fix:** use tested text/focus tokens for each surface and reserve lighter gold for decorative details. Verify actual adjacent background colors rather than treating a token as universally accessible.

**Acceptance:** measured text and focus contrast meets the applicable targets across default, hover, selected and error states on white and ivory.

### FE-014 — P2 — Admin creator exceeds a 320-pixel viewport

**Confidence:** high, reproduced. **Sources:** `src/app/admin/admin.module.css:31-43`, `:61-70`, `:267-286`; `src/app/admin/page.tsx:528-581`.

With the authenticated admin UI supplied by a browser fixture, a 320px viewport has `documentElement.scrollWidth === 351`. The creator card measures 335px wide from x=16 to x=351; its form fields extend beyond the right edge. The grid/card's intrinsic minimum sizing is not constrained sufficiently by the narrow-screen rules. The public routes tested at 320px did not exhibit page overflow; clipped carousel content alone was not counted.

**Impact:** narrow-phone and high-zoom users must pan horizontally to operate the form; parts of the form are outside the initial viewport.

**Fix:** allow grid tracks/cards/fields to shrink (`minmax(0, 1fr)` and appropriate `min-width: 0`), constrain file inputs, and preserve readable controls without clipping.

**Acceptance:** at 320 CSS pixels and desktop 400% zoom, the complete admin form reflows without horizontal page scrolling; controls and labels remain usable.

Evidence: [admin-overflow.json](frontend/admin-overflow.json), [admin-320.png](frontend/admin-320.png).

### FE-015 — P2 — Filters do not maintain a consistent URL/state model

**Confidence:** high, reproduced. **Sources:** `src/components/ProductList.tsx:29-34`, `:61-65`, `:95-103`; `src/app/page.tsx:30`.

From `/?category=rings#shop`, Reset filters shows eight products while leaving `category=rings` in the URL; reload returns to the empty Rings result. Choosing a category also changes the keyed ProductList instance, resetting locally held sorting/price selections. In the browser, “Price: high to low” became “Featured” after selecting Earrings.

**Impact:** users lose deliberate filter selections, copied links disagree with the visible results, and reload/back behavior is surprising.

**Fix:** use one consistent URL-backed filter model or explicitly preserve state when remounting; reset the corresponding query parameters when clearing filters.

**Acceptance:** sorting and maximum price survive category changes, reset updates the URL, and reload/share/back reconstruct the same results.

Evidence: [admin-filter-audit.json](frontend/admin-filter-audit.json).

### FE-016 — P2 — Completed order confirmation cannot be retrieved in the frontend

**Confidence:** high for the flow gap; no real payment executed. **Sources:** `src/app/checkout/page.tsx:203-205`, `:265-296`; `src/app/profile/page.tsx:90-119`.

A successful handler stores the display order number only in component state, clears the bag and switches an internal step. The URL remains `/checkout`. Reload/remount discards the confirmation and reaches the empty-cart view. Profile has no order history/detail/receipt route. This finding does not claim that the database order itself disappears or that no external receipt exists; it identifies the missing in-app recovery path.

**Impact:** customers can lose the order number/confirmation they were told to save and cannot revisit their purchase details from their account.

**Fix:** use a durable authenticated order-detail route keyed by the server's order ID, link it from confirmation/account, and reconcile pending/succeeded payment state on return.

**Acceptance:** reload, close/reopen, and return from payment can recover the correct order status and receipt; one customer cannot access another's order.

### FE-017 — P2 — Support and return promises have no usable customer path

**Confidence:** high, route/link inventory confirmed. **Sources:** `src/components/Footer.tsx:106-123`; `src/components/ProductDetail.tsx:400-403`; `src/app/checkout/page.tsx:206-208`; `src/app/profile/page.tsx:107-119`.

The site promises 30-day returns and tells customers with payment-verification trouble to “contact support,” but exposes no contact/support link, contact address, returns instructions or order-help route. Footer navigation only offers shopping/account destinations. No privacy/terms/shipping/returns page exists in the current route inventory. Legal sufficiency is outside this technical audit; the concrete defect is the missing route to exercise the displayed promise or resolve a failed payment.

**Impact:** customers with a paid-but-uncertain order or return request have no actionable next step on the site.

**Fix:** provide a reachable support channel and clear fulfillment/return information; link payment errors to a reference-bearing help action and link applicable policies at checkout/newsletter collection points.

**Acceptance:** every “contact support” or return promise has a working, keyboard-accessible destination with enough order context to request help.

### FE-018 — P3 — Metadata and catalog discovery are incomplete

**Confidence:** high for implementation observations; ranking/indexing impact not measured. **Sources:** `src/app/layout.tsx:20-24`; `src/app/product/[id]/page.tsx:24-31`; `src/components/ProductList.tsx:34`, `:168-180`; absence of sitemap/robots metadata files in `src/app` and public equivalents.

Login, wishlist, admin and checkout inherit the storefront title/description. No explicit canonical URLs, private/utility-route indexing policy, Product/Offer structured data, or sitemap is configured. Catalog expansion is a client button; the initial homepage exposes only its first eight grid products plus editorial links, so later items have no crawlable pagination link there. ### FE-020 — P2 — Purity-distinct variants can be unreachable in the product selector

**Confidence:** high for conditional selection logic; **not present in the inspected current catalog**. **Sources:** `src/components/ProductDetail.tsx:25-27`, `:59-76`, `:257-269`; `src/app/admin/page.tsx:279-288`. The backend's [schema-snapshot.json](backend/schema-snapshot.json) reports 25 products, 25 variants and no variantless products in the locally configured database: each inspected product therefore has one variant. This limitation requires a future/admin fixture with multiple colliding variants and is separate from reproduced current-catalog customer defects. The inspected database was not identified as production.

Selectors group only by metalType and size. `activeVariant` then returns the first matching row, ignoring purity and variant ID. If two variants share metal and size but differ in purity, only the first can be purchased; an in-stock second row can remain unreachable behind an out-of-stock first row. Admin permits multiple rows with the same metal name, so the UI can create this state. The final fallback to `variants[0]` also masks invalid combinations rather than showing them unavailable.

**Impact:** some legitimate catalog variants cannot be selected correctly; displayed options can diverge from the actual chosen SKU.

**Fix:** model selectable variant dimensions explicitly or select by a unique purchasable variant identity; never fall back silently to a different SKU.

**Acceptance:** fixture variants with shared metal/size and different purity are each selectable, correctly priced and added by the exact ID; invalid combinations remain unpurchasable.

## Architecture, motion and performance notes

- Shared Header/Footer and a root CartProvider/WishlistProvider/CartDrawer are sound reuse boundaries, but malformed local data currently has a root-wide blast radius (FE-010).
- ProductList performs all filtering/sorting over the entire serialized product catalog; Load More slices client data rather than fetching a page. Product detail loads all products to select one related item, and metadata/page both fetch the product without a React cache wrapper. These are scalability costs for backend review; no invented latency threshold or live production slowdown is asserted here.
- GoldOrbit dynamically imports Three.js, caps device pixel ratio at 1.5, uses an intersection observer, stops its continuous loop when hidden/offscreen, disposes resources and honors reduced motion. Hero pointer motion checks fine-pointer/hover support. Those are positive safeguards. No GPU/memory leak was demonstrated.
- Responsive product images generally use Next Image with appropriate source transformations. Source review found older raw-image usage in admin and non-transformed checkout thumbnails; these merit optimization when measured, but are not promoted to high-severity findings without load data.
- `error.tsx` uses supported `reset()` behavior. Server-data recovery may benefit from `unstable_retry()` in the installed Next version; this is a follow-up implementation choice, not proof of the historical product error.
- The 23 lint errors/10 warnings require cleanup, especially untyped API/state boundaries and effect-driven state updates. They are tracked in the parent baseline rather than inflated into 33 independent customer defects.
